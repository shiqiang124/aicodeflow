## 1. 开始前

- 先确认任务等级（L1/L2/L3）和输入：L1 读取 Issue；L2/L3 读取需求仓库 `docs/requirements/REQ-<编号>/REQ.md`，同时读取同一需求目录中已保存并确认的 `PLAN.md`；L1 不要求持久化 Plan。
- **先读取真实代码**，不得虚构文件、接口、配置或既有行为；无法确认的内容列为待核实项，而不是猜测。
- 方案经开发负责人确认后再编码；L3 方案需技术负责人参与确认。

## 2. 实施边界

- 只在独立任务分支或 worktree 工作；不得直接提交、合并到受保护分支，不得创建发布 tag 或批准发布。
- 只修改与任务相关的文件；不得自行扩展业务范围、自行设计未定义的业务行为，不得修改已执行的数据库迁移脚本。
- 优先编写能表达 AC 的测试，再修改实现；禁止删除测试、弱化断言或用无依据的 try/catch、判空来“消除报错”。
- 不得生成、提交或打印密钥、token 和生产凭据。
- 提交前用 `git status` 核对改动，只暂存相关文件；提交信息使用 Conventional Commits，例如 `feat: 新增运动分享接口 (#133)`。

## 3. 遇到偏离立即停下

- **业务变化**（范围、用户行为、AC、设计口径）：停止受影响部分，交由产品更新 REQ。
- **关键技术变化**（API/协议/数据契约、兼容/回滚、架构关键决策）：停止受影响部分，交由开发负责人确认新方案（L3 由技术负责人参与）。
- L2/L3 的业务或关键技术方案变化必须同步更新原 `PLAN.md` 并按等级确认后继续；业务变化同时更新、确认 REQ。验证结果仍留在 PR/CI/测试系统，不回填 Plan。
- **边界内调整**（等价重构、辅助测试、文件组织）：可继续，在 PR 中简述差异。

## 4. 验证与 PR

- 运行构建、lint、相关测试；需要真机/BLE/外部系统时写明人工验证步骤。
- 如实记录结果：通过 / 失败 / 未执行（原因）；不得把未执行写成通过。证据对应实际验证的 SHA、构建号与环境。
- PR 描述按团队模板填写：关联 Issue/REQ 与 Plan 链接（L2/L3）或方案要点（L1）、AI 参与、变更范围、与方案的差异、兼容与回滚、验证结果、发布影响。Bug 修复写明根因、复现步骤和回归验证。
