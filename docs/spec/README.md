# AI 辅助开发流程（10 人团队精简版）

> 目标：**AI 先行、人工把关、证据留在原位、减少重复审批**。适用于后端 / Web、Flutter App、设备协作需求。
>
> 本文件是流程与职责的唯一规则来源；`1_REQ-template.md`、`2_PLAN-template.md` 是填写模板；`AGENTS.base.md` 是业务仓库 AI 约束的通用原始版本；`3_项目分支与发布规范.md` 规定 Git、CI 和发布；`4_特殊发布操作手册.md` 仅用于特殊发布场景。

## 0. 仓库与信息归属

| 位置 | 存放内容 | 谁维护 |
| --- | --- | --- |
| 需求仓库 `docs/requirements/REQ-<编号>/REQ.md` | 已确认业务需求与 AC、设计版本/资料 | 产品负责人 |
| 需求仓库 `docs/requirements/REQ-<编号>/PLAN.md` | L2/L3 必需的持久化方案及确认记录 | 开发负责人 |
| 业务仓库 / 任务分支 | 业务实现及其工程配置，包括代码、自动化测试、CI、`AGENTS.md` | 开发 / Codex |
| 业务仓库代码 PR | Plan 链接（L2/L3）、方案要点（L1）、实施差异、验证命令及结果、CI 链接、关联需求、发布影响 | 开发负责人 |
| CI / 测试系统 / 发布记录 | 自动化验证、人工测试结果、构建 SHA 与制品、上线与回滚记录 | CI / 测试 / 发布负责人 |

**单一事实来源**：REQ 管业务要求；Plan 管已确认的实施方案；PR 管实际代码变更；CI/测试系统管验证事实；发布系统管制品及上线状态。L2/L3 必须在需求仓库保存 Plan，并在关键方案变更时更新；不要求另建独立 Plan 审批 PR、不回填测试结果。

每个 L2/L3 需求维护一份持久化 `PLAN.md`，与 `REQ.md` 同级；跨仓库或分阶段实施在同一文件中分节描述，方案调整直接更新该文件。L1 不要求持久化 Plan。

L2/L3 编码前必须已保存并确认 Plan，不能仅留下任务分支或会话中的草案。代码 PR 引用 Plan 链接并说明实际实施差异，不重复完整方案，不向业务主干合入 Plan 文件。

**需求仓库协作**：需求仓库 `main` 受保护，禁止直接 push。每个需求使用一个需求分支（如 `req/REQ-123`）修改 REQ 及 L2/L3 Plan，尽早创建草稿 PR；产品负责人在该 PR 中确认 REQ 后业务基线即生效，L2/L3 方案确认记录在 Plan 中。分支上的内容全部完成后，REQ 与 Plan 通过同一个 PR 合并到 `main`，由该需求的开发负责人合入，不要求额外的非作者 Review。合入后若发生 A 类业务变更，另开需求分支和 PR，经产品确认后合入。

`AGENTS.md` 是业务仓库的 AI 约束入口；跨仓库通用规则以需求仓库 `docs/spec/AGENTS.base.md` 为唯一原始版本。业务仓库 `AGENTS.md` = 同步的通用部分 + 本仓库特有的目录、命令和约束；通用部分采用脚本同步或 CI 检查一致性，不在业务仓库手工修改。

## 1. 先按风险分级，再选流程

| 等级 | 典型场景 | 必需记录 | 执行流程 |
| --- | --- | --- | --- |
| **L1 快速任务** | 文案、局部 UI、普通 Bug、小型重构；通常半天内且低风险 | Issue/PR 写明预期、方案要点、验证及结果 | 问题描述 → Codex 读代码/给方案 → 开发快速确认 → 实现与测试 → PR/CI/Review |
| **L2 常规需求（默认）** | 独立页面、API 扩展、普通业务逻辑；通常 0.5–3 天 | REQ + AC；持久化轻量 Plan（四段即可）；代码 PR、测试证据 | REQ 确认 → AI Plan → 开发确认 → 编码与自测 → PR/CI/Review → 按需联调 → 产品需求预验收 → 提测/测试验收 → 发布 → 产品线上验收 |
| **L3 复杂/高风险** | 多仓库强耦合、设备/固件协议、OTA、支付/权限安全、不可逆数据迁移、重大兼容/回滚风险 | REQ、持久化 Plan、契约/风险/回滚、明确验证记录 | 需求评审 → 技术方案评审 → 分阶段实施 → CI/Review → 必要联调 → 产品需求预验收 → 提测/专项测试验收 → 发布审批 → 产品线上验收 |

- **时间是工作量估算，不是安全豁免**。2 小时的数据迁移也可为 L3；4 天可独立验收的普通页面可为 L2。
- 跨端但接口向后兼容、职责明确、无高风险的任务可为 L2；有强耦合或联合发布风险时升级 L3。
- 产品负责人和开发负责人在开始时共同确定等级；执行中出现高风险、需求歧义或不可回滚风险时立即升级，暂停受影响部分。
- L1 不创建 REQ/Plan；若涉及业务行为改变，先明确预期并由产品确认。L2/L3 必须具有可验证的 AC。

## 2. 需求确认与拆分

1. 产品填写 `1_REQ-template.md`：目标、范围/不做、已有行为变化、AC、约束、设计版本和未决业务问题。**只写业务**，不指定类名/表结构等实现细节。
2. L2 允许异步评论确认；L3 或存在分歧时召开评审。产品负责人在需求分支 PR 中确认 REQ 后，业务需求基线生效（合入规则见 §0）。业务阻塞问题须清零；非阻塞问题标明责任人和处理时点。
3. 拆分优先看**可独立验收、依赖明确、发布可控**。AC 超过 20 条或估算超过 3 天只是提醒，不强制拆分；不按技术端机械拆分。无法独立上线的多个任务，应声明联合验收与发布策略。
4. 设计图标明固定版本或导出文件；默认/加载/空态/失败状态如未设计，必须明确沿用已有组件规则或登记待确认，Codex 不自行设计业务行为。

## 3. AI 分析、Plan 与实施

1. 开发把 REQ 路径、业务仓库路径与相关设计/契约交给 Codex。AI **先读取真实代码**，不得虚构文件、接口或既有行为。
2. Codex 使用 `2_PLAN-template.md` 为 L2/L3 生成并保存 `docs/requirements/REQ-<编号>/PLAN.md`。L2 用四段轻量方案：改什么/为什么、契约与风险、AC 对应验证、开发确认记录，不必填写完整表格。L3 用完整 Plan，包含真实代码现状、改动步骤、契约/兼容、AC→测试、风险及未决问题。
3. **编码前确认关键方案**。开发负责人默认指该任务的开发负责人，L1/L2 由任务负责人确认；L1 可在会话/PR 中快速确认，不要求持久化 Plan。L2 可在 Issue/PR 评论或 Codex 会话确认，但结论必须写入持久化 Plan。L3 由技术负责人参与确认关键契约、数据变更和回滚策略，确认记录同样留在 Plan。无需另建独立 Plan 审批 PR。
4. Codex 在独立任务分支或 worktree 实施；优先写能表达 AC 的测试，再改实现。已覆盖或无法自动化时记录依据和可执行的人工验证。不得修改无关文件、历史已执行的迁移脚本或自行扩展业务范围。
5. PR 可提前创建为草稿，逐步补齐构建、lint、相关测试和必要的真机/BLE 验证；失败必须记录，不能将未执行写成通过。AI 可在约定范围内迭代修复；禁止删除测试、弱化断言以“刷绿”。
6. 开发人员对 AI 改动负责；**必需 CI、相关开发验证通过 + 非作者 Review** 后合并。记录失败不等于允许带失败合入。小 PR 优先，但不采用机械的 400 行硬门槛；大 PR 需要可审查的变更说明，必要时拆分。

## 4. 执行中偏离：按影响处理

| 类型 | 判断 | 动作 |
| --- | --- | --- |
| **A 业务变化** | 范围、用户行为、AC、设计口径变化 | 暂停受影响部分；产品更新 REQ 并确认；更新实施方案与测试 |
| **B 关键技术变化** | API/协议/数据契约、兼容/回滚、架构关键决策变化 | 暂停受影响部分；开发负责人确认新方案（L3 由技术负责人参与确认）；通知消费方并补验证 |
| **C 边界内调整** | 等价内部重构、辅助测试、文件组织等，不影响业务和契约 | 允许继续；在 PR 简述重要差异，无需回填 Plan |

有疑问时先询问开发负责人；业务疑问由产品确认。L2/L3 的 A/B 方案变更均同步更新原 Plan，并按等级确认后继续受影响部分；A 同时由产品更新并确认 REQ，B 由任务负责人确认（L3 由技术负责人参与）。合入后的 Plan 更新另开需求分支和 PR，沿用 §0 的合入规则；C 类调整仍仅在代码 PR 简述。

## 5. 代码 PR 归档实际实施与验证

代码 PR 模板最少包含：

```markdown
## 关联
- Issue / REQ：
- Plan 链接（L2/L3 必填；L1 写方案要点，无需 Plan 文件）：
- AI 参与：是 / 否
## 实施
- 变更范围与关键设计：
- 与确认方案的重大差异（无则写无）：
- API/数据/设备协议兼容及回滚（不涉及时写不涉及）：
## 验证
- 命令 / 场景：
- 结果：通过 / 失败 / 未执行（说明原因）
- CI 链接、验证 SHA、真机/环境信息（适用时）：
## 发布影响
- 是否需要联调、功能开关、迁移、特殊发布顺序：
```

Bug PR 记录**根因、复现步骤、回归验证**。跨仓库 PR 互相链接；跨端一致性由一个明确的联调负责人负责。AI 标记用于 Review 聚焦，不替代安全检查。

## 6. 验收与发布（按风险裁剪，不复制测试记录）

| 检查点 | L1 | L2 | L3 | 证据的唯一位置 |
| --- | --- | --- | --- | --- |
| 开发自测 | 必需，按影响范围 | AC 对应验证 | AC/边界/契约完整覆盖 | PR、CI |
| 联调 | 仅受影响时 | 跨端或关键路径需要时 | 按计划执行 | 联调记录或关联 PR |
| 产品需求预验收 | 涉及业务体验时，在合入或发布前由产品确认 | 提测前确认需求结果，可与开发自测或预联调同轮完成 | 提测前完成业务和设计关键点确认 | 需求/测试系统链接 |
| 测试验收 | 按变更风险 | 测试执行必要回归 | 专项 + 集成 + 回归 | 测试系统 |
| 产品线上验收 | 涉及业务体验时，上线后由涉及业务的产品验收受影响体验 | 上线后，涉及业务的产品验收需求关键路径 | 上线后，涉及业务的产品验收业务和设计关键点 | 发布记录中的验收结论或证据链接 |

- L2/L3 的顺序为：产品需求预验收（提测前）→ 测试验收（提测后）→ 上线 → 涉及业务的产品线上验收；不涉及业务的工程变更按影响范围完成技术验证。后端/Web 的产品需求预验收在 dev 环境进行，推广到 test 环境即为提测；App 按 `3_项目分支与发布规范.md` 的冻结与 RC 流程执行。
- **App 版本功能冻结前**，计划交付的需求须完成产品需求预验收、开发自测与必要联调；冻结后进行版本集成/回归和提审，沿用 `3_项目分支与发布规范.md`。
- 提测前开发侧阻塞项须清零；上线前测试侧及发布侧阻塞项须清零。失败或未执行的阻塞验证不能仅靠记录原因放行；修复或完成验证后复测受影响 AC。证据须对应**实际测试代码 SHA / 构建号 / 环境**，不能以旧 Plan 基线 SHA 代替。
- 产品需求预验收不替代测试人员的回归；产品线上验收关注实际业务结果，不重跑所有 AC。发布负责人仍负责技术发布检查与回滚准备，不代替产品线上验收。

## 7. 团队职责与落地顺序

| 角色 | 核心责任（允许一人兼岗，但代码 Review 不得由作者自己完成） |
| --- | --- |
| 产品负责人 | 需求范围、AC、设计版本、业务变更；组织提测前产品需求预验收，上线后由涉及业务的产品完成线上验收 |
| 开发负责人（任务负责人） | 本任务分级、L1/L2 方案确认、技术风险、Codex 结果与代码质量；将完成的需求分支合入需求仓库 `main` |
| 技术负责人 | 参与 L3 关键方案及重大技术变更确认，不集中审批所有 L1/L2 任务 |
| PR Reviewer | 非作者 Review，关注逻辑、安全、兼容与边界 |
| 测试人员 | 关键路径、异常和版本回归；保留可追溯证据 |
| 发布负责人 | 受保护分支、RC/tag、生产审批、回滚与回补 |

**分三步实施**：① 先启用 L1/L2/L3、精简模板和 PR 检查项；② 统一 AGENTS.md，逐步建设下述 Skills；③ 依据实际瓶颈再做 Backport、验证摘要和 CI 失败诊断自动化。不因 Skill 未完善而绕过已有 CI、Review 和发布控制。

### 拟建设 Codex Skills（不作为上线前置条件）

以下是能力规划及建议名称，不代表已安装或可直接调用；实施时先确认实际可用能力。

| Skill | 输入 → 输出 | 人工介入点 |
| --- | --- | --- |
| `/analyze-req` | REQ + 代码 → 风险清单 / Plan 草案 | 需求歧义、技术方案确认 |
| `/implement` | 已确认方案 → 代码和相关测试 | 契约或业务变化时停下 |
| `/verify` | 变更 → 构建、测试与证据摘要 | 失败反复、需真机/外部系统时 |
| `/prepare-pr` | 实际 diff + CI → PR 描述/检查项 | 人工 Review、合入 |
