# AI 辅助开发流程

- [需求模板](1_REQ-template.md)用于编写 L2/L3 的 REQ，填写后上传到需求管理平台。
- [分支与发布规范](2_项目分支与发布规范.md)规定 Git、CI、合并和常规发布。
- [特殊发布操作手册](3_特殊发布操作手册.md)适用于紧急修复、回补及 RC 异常。

业务仓库各自维护 `AGENTS.md`，记录目录、构建与测试命令、环境和模块约束，并链接本流程及分支规范。

## 分级与确认

| 等级 | 适用场景 | 编码前确认 |
| --- | --- | --- |
| L1 快速任务 | 文案、局部 UI、普通 Bug、低风险重构 | 在 Issue 或草稿 PR 中记录预期、方案要点和确认结论，由任务开发负责人确认方案。涉及业务行为变化时先由产品确认预期 |
| L2 常规需求 | 独立页面、兼容的 API 扩展、常规业务逻辑 | 产品在平台确认 REQ 和可验证的 AC，任务开发负责人确认方案。可异步确认 |
| L3 复杂或高风险 | 多仓库强耦合、设备协议、OTA、支付或权限、不可逆迁移、联合发布或重大兼容风险 | 产品组织需求评审并在平台确认 REQ，任务开发负责人和技术负责人共同确认关键契约、兼容、风险及回滚方案 |

产品和开发按风险共同分级。出现需求歧义、新的高风险或不可回滚风险时，暂停受影响部分并重新评估等级。需求按可独立验收、依赖明确、发布可控的原则拆分。确认前清除业务阻塞项，其他问题明确负责人和处理时点。设计资料使用平台附件或固定版本链接，未覆盖的界面状态应注明沿用的规则或交由产品确认。

## 实施与变更

- 开发提供业务仓库路径。L1 提供 Issue 或草稿 PR 链接，会话中的确认结论在编码前补到所选记录。L2/L3 提供平台需求链接和相关设计、契约资料。AI 先读实际代码，记录待核实项。L2/L3 的方案应为每条适用的 AC 明确验证方式，L3 同时说明实施步骤和未决风险。
- L2/L3 由任务开发负责人在编码前把已确认的 REQ 版本、方案版本和确认结论记入同一平台条目。用固定版本链接或可回查的附件版本标识引用原文，方案可引用关联 Issue、独立方案文档或已有的 `PLAN.md`。会话中的确认结论也在编码前补到平台。
- 在任务分支或 worktree 实施，优先编写能表达 AC 的测试。已有测试覆盖可引用，无法自动化时说明原因并提供可执行的人工验证步骤。修改限于已确认范围，保留已执行的迁移脚本和有效的测试断言。
- **A 类业务变化**（范围、用户行为、AC、设计口径）暂停受影响部分，由产品在平台更新 REQ 并重新确认，开发同步更新方案和测试。
- **B 类关键技术变化**（接口、协议、数据契约、兼容、回滚或架构）暂停受影响部分，由开发负责人确认新方案，L3 由技术负责人参与。通知受影响的调用方并补验证。
- L2/L3 发生 A/B 类变更时，由任务开发负责人在同一平台条目追加新方案版本和确认记录。A 类同时记录新 REQ 版本及产品确认。保留历史记录，按等级完成确认后再继续受影响部分。
- **C 类边界内调整**（等价重构、辅助测试、文件组织）可继续，在代码 PR 中简述重要差异。

## 代码 PR 与验证

- L1 在代码 PR 写明方案要点，已有 Issue 时附链接。以草稿 PR 发起的任务在该 PR 中保留预期和确认结论。L2/L3 链接平台条目及实际实施所依据的 REQ 和方案版本确认记录。注明 AI 参与、变更范围、与确认方案的重大差异，以及兼容、回滚和发布影响。Bug 修复记录根因、复现步骤和回归验证。跨仓库 PR 互链，跨端联调明确负责人。
- 补齐构建、lint、相关测试以及适用的真机或联调验证。记录命令或场景、通过/失败/未执行及原因、CI 链接，以及适用的实际验证 SHA、构建号和环境。验证证据留在代码 PR、CI 或测试系统。
- 代码合并须通过必需 CI、相关开发验证和非作者 Review。发布按分支规范执行，制品及上线状态记录在发布系统。

## 验收

- 开发先自测，跨端和关键路径按需联调。L3 按方案覆盖 AC、边界及契约，并完成专项验证。
- L2/L3 先由产品做需求预验收，再提测并由测试验收。后端和 Web 在 dev 预验收，推广到 test 即提测。App 在功能冻结前完成预验收、自测和必要联调，冻结及 RC 按分支规范执行。
- 提测前清除开发侧阻塞项，上线前清除测试和发布侧阻塞项。修复后复测受影响的 AC。上线后，由涉及业务的产品负责人验收关键业务路径。L1 按影响范围验证，涉及业务体验时由产品在合入或发布前确认，并在上线后验收。
