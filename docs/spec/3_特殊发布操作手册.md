# 特殊发布操作手册（按需查阅）

> 配合 `2_项目分支与发布规范.md` 使用。本文只涵盖生产基线、特殊回补、例外批准与基线核验；日常开发请优先走日常版，不要默认使用这些流程。所有示例版本/SHA 均为占位符。

## 0. 共同前提

- 发布负责人掌握受保护 `release/*`、`hotfix-base/*` 的创建/删除及发布 tag 权限，AI 账号不得拥有这些权限。
- 基线发布、热修必须基于**实际线上版本 tag / SHA / 制品**核验，而不是猜测当前分支 HEAD 即生产版本。App 只维护一个线上系列，热修目标为当前线上系列对应的 `release/x.y`。
- 所有已推送的 `v*` tag（包括 RC 和取消版本）不得移动、删除或复用。
- 合入前必需 CI、相关开发验证通过；提测前开发侧阻塞项清零，上线前测试侧及发布侧阻塞项清零。上线后由涉及业务的产品完成线上验收，结果链接到发布记录。
- 修复 PR 保留根因、风险、回归测试、影响版本和回补目标；受保护分支必须通过最新合并候选的 CI 和非作者 Review。
- 无法保证最新合并候选检查的 Git 托管平台，关闭自动合并，由发布负责人串行合并、合并前核对源/目标 SHA，合并后复验 tree/diff。

## 1. 后端 / Web 临时生产基线 hotfix

**触发条件**：线上紧急问题必须修复，但 `main` 含有尚不能发布的改动，且无法安全通过功能开关、revert 或已验证制品解决。

1. 从发布记录确认当前生产 `v1.8.0` 的 SHA 和制品；先核对问题和修复范围。
2. 发布负责人从生产 tag 创建并保护 `hotfix-base/v1.8.0`。
3. 开发从该基线创建 `hotfix/ISSUE-225-login-npe`，补回归验证后提 PR 至 `hotfix-base/v1.8.0`。
4. 合并候选通过 CI/Review；发布**从该基线提交构建并验证的同一制品**，审批后生产上线，按实际生产 SHA 打新 patch tag（如 `v1.8.1`）。
5. 尽快回补 `main`（必要时适配，不盲目 cherry-pick）；默认**生产发布当天**完成并验证。关闭回补及相关发布记录后，发布负责人删除临时基线分支，保留 tag。

```bash
# 由发布负责人执行
git fetch origin --tags
git branch hotfix-base/v1.8.0 v1.8.0
git push -u origin hotfix-base/v1.8.0

# 由开发执行
git fetch origin
git switch -c hotfix/ISSUE-225-login-npe origin/hotfix-base/v1.8.0
# 修改、测试、提交、推送，PR → hotfix-base/v1.8.0
```

如果需要从 main 部分撤销未验证功能，必须经过独立 revert PR/CI/Review，不能直接修改生产分支或移动生产 tag。

## 2. App 方案 B：先修 release，再回补 main

**触发条件**：修复无法在 main 上及时独立完成，或两者差异使先 main 再回补不适用。

1. 发布负责人从发布记录确认线上正式 tag、源码 SHA、制品；检查目标 `release/x.y` 的 HEAD 与线上版本关系。通常 HEAD 应与线上 tag 相同；若历史上已有未发布修复，须先明确隔离/撤销策略，不能混入本次热修。
2. 从**已核验的 release HEAD** 切独立 `hotfix/*` 任务分支，回归测试后 PR 到对应 `release/x.y`；审查差异仅包含本次修复。
3. 合并前检查最新源/目标 SHA、线上 tag 是否改变；发生变化须重新核验。合并后记录 release 修复的最终 SHA。
4. 从修复 SHA 向 main 提交回补 PR；发生冲突须适配并重新验证。main 采用 Squash 时，在 PR/最终提交说明保留 release 来源 SHA 链接。
5. RC、提测、提审、发布按日常规范；App 的回补默认**提审前完成并验证**，例外见 §3。

**禁止**直接从过期的生产 tag 做热修，却把不包含后续 release 改动的结果直接强推覆盖 `release/x.y`。

## 3. 回补期限与例外批准

- App 默认在**提审前**完成全部必需回补及验证；后端/Web 临时生产基线默认在**生产发布当天**完成。
- 无法按期安全完成时：先创建回补 PR，记录**原因、PR 链接、负责人、目标完成时间、受影响版本、风险缓解措施**。
- 指定一名**非本次发布负责人的例外批准人**作出确认；App 在提审前批准，后端在当天截止前批准。人手少可由另一名有权限的负责人兼岗，但不能自行批准自身例外。
- 期限前完成合入与验证；仍无法完成须在到期前重新评估并批准延期。异常期间发布清单标注未关闭的回补项。

## 4. App 热修、取消 RC 与基线一致性

### 热修版本

- 线上正式版如 `v2.3.0`，热修版本递增为 `2.3.1`。先通过 PR 更新 `release/2.3` 版本号，再打 `v2.3.1-rc.1` 提测。
- 一次补丁正式 tag 发布后，不得复用该补丁号；只取消 RC、从未打正式 tag 时可保留该补丁版本号，但必须采用未使用的下一个 RC 序号。
- 同一系列中并行热修须串行确定候选版本，不能让较旧的热修覆盖已上线的较新热修。

### 取消 RC 或撤销未发布变更

- 对已合入 release、但不应随发的修复或版本号变更，通过**revert PR** 撤销，禁止改写发布历史。
- 由发布负责人核验当前线上正式 tag 是否是 release HEAD 的祖先；如果 HEAD 不同但声称内容一致，应检查 Git tree SHA，并审查相对于线上 tag 的实际差异。内容不一致或来源无法证明时先停止发版。
- 同一 RC tag 不可改指向；任何源码变化都打新 RC tag 并重新验证受影响范围。

示例核验命令：

```bash
git fetch origin --tags
git rev-parse 'v2.3.0^{commit}'
git rev-parse origin/release/2.3
git merge-base --is-ancestor 'v2.3.0^{commit}' origin/release/2.3
# 仅在预期 release 与线上内容等价时比较 tree SHA
git rev-parse 'v2.3.0^{tree}'
git rev-parse 'origin/release/2.3^{tree}'
git diff v2.3.0 origin/release/2.3 --stat
```

**注意**：提交 SHA 不同但 tree 相同，并不意味着回补来源、版本链路或发布时间已经合规；还应核对发布记录、修复 PR 和相关回归测试。

## 5. Cherry-pick 与来源校验

```bash
# 从 main 合入后的 squash SHA 回补 App release
git fetch origin
git switch -c cp/ISSUE-224-to-2.3 origin/release/2.3
git cherry-pick -x <main-squash-SHA>
# 冲突时：解决文件 → git add <文件> → git cherry-pick --continue
# 推送并提 PR，目标 release/2.3
git push -u origin cp/ISSUE-224-to-2.3
```

- `-x` 追加来源说明，便于追溯；Cherry-pick 生成的新提交 SHA 本来就不同于原提交。
- 推荐一个回补 PR 对应一个原始修复提交；多个修复依次处理，减少回溯歧义。
- 优先用保持提交正文可追溯的合并策略；若平台仅支持 Squash，应明确在最终提交或关联 PR 中保留来源 SHA，并由 CI/Reviewer 核查，**不要仅凭合并按钮名称推断保留了 SHA**。
- 来源 SHA 必须存在于目标来源分支（默认 main），回补 diff 需在当前 release 上重新测试；来源有过后续 revert/修正时核对当前行为，而不是只检查 SHA 存在。

## 6. 发布清单（特殊发布必须填写）

```markdown
- 类型：后端生产基线 / App 先 release 热修 / 回补例外 / RC 取消
- 线上基线：tag、提交 SHA、当前制品 ID
- 候选：分支、RC/tag、提交 SHA、tree SHA（适用时）、构建号、制品 ID
- 变更和测试：PR 列表、回归/联调链接、CI 结果
- 兼容与恢复：旧版本支持范围、迁移影响、回滚/热修方法
- 回补：目标分支、PR、来源 SHA、状态/完成期限
- 审批：发布负责人、例外批准人（若需要）、审批时间
- 发布：环境、部署制品、发布时间、验证结论
```

发布、回补和审批记录留在发布清单及对应的 PR 中。
