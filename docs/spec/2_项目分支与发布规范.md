# 项目分支与发布规范（日常版）

> 适用：Server / Web（Java、Vue 等）和 App（Flutter、iOS、Android）；Server/Web 与 App 独立仓库、独立 `v*` tag 序列。
> 本文定义**日常必遵守规则**；低频异常操作见 `3_特殊发布操作手册.md`。AI 开发流程与分级以 `README.md` 为准。

## 1. 两种发布模型

> **通用不变式**：所有已推送的 `v*` tag（含 RC 和取消版本）不得移动、删除或复用；App 的 RC tag 指向候选制品的源码提交，正式 tag 在实际上线后指向已上线制品的源码提交。

### Server / Web：主干开发，环境是流水线阶段

```text
feature/*、bugfix/*、hotfix/*
               └─ PR + CI + Review + Squash → main → build once
                                                   ├→ dev
                                                   ├→ test
                                                   └→ prod（人工审批上线）→ v* tag
```

- 同一个已验证的**不可变制品**逐环境推广，不重新以当前 main 构建另一份制品。
- 环境与验收对应：**dev** 进行开发自测、联调和产品需求预验收；推广到 **test** 即为提测，由测试执行验收；test 侧阻塞项清零后经人工审批推广到 **prod**，上线后由涉及业务的产品完成线上验收。
- 生产 tag 标记**实际生产运行的提交 SHA**；记录制品标识、部署环境、发布人和结果。
- 生产紧急修复优先先进 `main`，再加急验证和发布；若 main 有不能随发的变更，使用 `3_特殊发布操作手册.md` 的生产基线方案。

### App：main 持续开发，release 冻结维护

```text
main ──●──●──●──●──●────────→ 下一版本功能
              ╲
               release/2.3 ──●──●────→ 2.3.0 RC / 正式版及 2.3.x 热修
```

- 开发在 `main`；版本内容已达到冻结条件时，从**记录的冻结 SHA** 创建 `release/x.y`。
- `release/x.y` 只承接本系列的 bug 修复与必要版本号变更，不再接新功能；main 继续下一版本。
- App 版本先打 `vX.Y.Z-rc.N` tag，再从其固定提交构建、提测、提审；实际上线后，正式 `vX.Y.Z` tag 指向已上线制品对应的 RC 提交。
- 同一 RC tag 重新构建也要分配新的构建号并记录制品标识；正式发布必须使用实际审核通过的制品。

## 2. 日常分支与提交

**合并门槛**：PR + 必需 CI + 相关开发验证通过 + 非作者 Review，常规使用 Squash；合并前核对最新目标基线。本文的“合并门槛”均指此定义。

推荐分支：`feature/REQ-123-share-api`、`bugfix/ISSUE-224-crash`、`hotfix/ISSUE-225-login-npe`。唯一编号足够时不强制包含姓名与日期。临时任务也先创建 Issue；分支名可用短描述加日期避免重名。

提交信息遵守 Conventional Commits，例如：

```text
feat: 新增运动分享接口 (REQ-133)
fix: 修复分享图片崩溃 (#224)
refactor: 整理登录逻辑 (#238)
```

允许 `feat` / `fix` / `refactor` / `test` / `docs` / `chore` / `revert`。PR 标题尽量作为 Squash 提交信息。

REQ 编号必须使用 `REQ-133` 格式（如 `feat: 新增运动分享接口 (REQ-133)`），需求管理平台按 `REQ-` 前缀把提交、PR 和发布 tag 关联到需求条目；纯 Bug 任务的 Issue 编号用 `#133` 格式。Squash 合并后的最终提交信息也必须保留编号；分支名不强制带编号。

### 开发与合并（Server / Web / App 通用）

```bash
git fetch origin
git switch main
git pull --ff-only origin main
git switch -c feature/REQ-123-share-api # 创建并切换
# AI / 开发修改并测试
git add -A && git commit -m "feat: 新增运动分享接口 (REQ-133)"
git push -u origin feature/REQ-123-share-api
# 创建 PR，按合并门槛合入（Squash）
```

- 分支仅针对一个可审查的任务；合入后删除任务分支，不在已 Squash 的旧分支继续开发。
- 开发中需同步 main 时可 `git fetch origin && git merge origin/main`，避免在多人共享分支上随意改写历史。
- **多个 AI 会话并行时用独立 worktree + 独立分支**；单任务不强制使用 worktree。分支基于最新 main，合并前核对当前工作区与未提交改动。

示例：

```bash
git fetch origin
git worktree add ../repo-req123 -b feature/REQ-123-share-api origin/main
# 完成后确认已提交/推送/合并，再清理
git -C ../repo-req123 status --short
git worktree remove ../repo-req123
git branch -D feature/REQ-123-share-api
```

## 3. 仓库保护与权限（一次性平台配置）

| 对象 | 必须保护 |
| --- | --- |
| `main` | 禁直接 push/强推；按合并门槛（§2）；合并前验证最新目标基线 |
| `release/*`（App） | 禁直接 push/强推；按合并门槛（§2）；只准发布负责人创建/删除 |
| `hotfix-base/*`（Server/Web，若使用） | 同 release，专用紧急发布基线 |
| `v*` tag | 保护创建权限；不变式见 §1 |
| AI 账号 / token | 只可在任务分支工作，不能合并受保护分支、创建发布 tag 或批准生产发布 |

- 平台支持合并队列时，对 release/hotfix-base 使用**目标 SHA 最新、合并候选验证**机制；不支持时关闭自动合并，由发布负责人串行控制合并，核对最新的源/目标 SHA 和必需检查，合并后复验 tree/diff，避免 CI 校验旧代码却合并新代码。
- `main` 可启用合并队列以减少“保持最新”的反复手工 merge。CI 必须在合并候选或对应有效提交上通过。
- 静态扫描、相关测试、构建和密钥扫描设为必要检查；涉及数据库迁移时增加**已执行迁移文件不得被修改**的 CI 检查。

## 4. PR / AI 协作要求

- **所有代码变更**都经过 PR 并按合并门槛（§2）合入，包括 AI 生成代码。
- PR 描述按[各阶段要求](README.md#各阶段要求)填写。
- 不强制“超过 400 行必须拆 PR”，但大规模、跨模块、难以审查的变更须拆分或解释；禁止借任务大规模重写无关代码。
- 修 Bug 须给出根因、复现方式和回归验证；不能仅用无依据的 try/catch、判空“消除报错”。
- AI 不得生成、提交或在日志及其他输出中打印密钥、token 和生产凭据。本地和 CI 做密钥扫描，已执行的迁移脚本不可被覆写。
- 产品、开发和测试的验收责任见 `README.md`；合入并不自动等于验收通过。

## 5. App 常规冻结、修复和发布

### 冻结条件

- 该版本功能已合入 main；做不完的功能明确移出版本或在发布时默认关闭。
- main CI、开发自测、必要联调通过；计划交付需求完成提测前的**产品需求预验收**。
- 冒烟用例可通过，无已知阻塞级问题；发布负责人记录**冻结 SHA**，据此创建 `release/x.y`。
- 冻结后进入候选版本测试：发现 bug 是正常过程，但不再混入新需求。

### release 期间的 bug 修复

**默认先 main，后 release：**

1. 从 main 修 Bug 并按合并门槛合入，记录 squash 提交 SHA。
2. 从目标 `release/x.y` 创建 `cp/*` 分支，使用 `git cherry-pick -x <main的squash SHA>` 回补；按合并门槛合入 release。
3. 验证 release 修复，并按需打下一 RC tag 提测；避免因多个版本遗漏修复。

如代码差异不适合先 main，按 `3_特殊发布操作手册.md` 的 App 方案 B；回补期限与来源追溯见同文 §3、§5。

### RC / 提审 / 正式发布

1. 版本号在 release 里通过 PR 更新；CI 分配每次构建唯一构建号。
2. 发布负责人为 release 上的候选 SHA 打 `v2.3.0-rc.1`；依次使用 `rc.2`、`rc.3`，不移动旧 tag。
3. 测试针对候选制品完成验证并记录：RC tag、源 SHA、构建号、平台制品标识、测试结论。
4. 使用**已通过测试的制品**提审；平台要求重构建时从同一固定源码重建，重新冒烟，记录新的构建号/制品。
5. 审核通过后，测试侧及发布侧阻塞项清零并完成生产审批，上线实际获审制品；实际上线后将正式 `v2.3.0` tag 打到**已上线制品对应的 RC 提交**，记录发布时间、审批和结果。上线后由涉及业务的产品完成线上验收；有 REQ 时结论记入平台需求条目，纯 Bug 任务记入对应 Issue、PR 或发布记录，证据链接保留在发布记录。

团队只维护一个线上 App 系列；正式发布后热修只加入**当前线上系列**对应的 `release/x.y`，patch 版本号递增；热修具体基线与回补规则见 `3_特殊发布操作手册.md`。

## 6. 跨端兼容、回滚与记录

- API / 数据库变化须兼容仍在支持期的 App；先发布兼容新旧客户端的服务端，再发布依赖该契约的 App。必要时通过功能开关隔离未完整联调的功能。
- 业务 PR 明确跨端联调负责人、发布顺序、客户端/固件支持范围与失败恢复方法。
- Server/Web 回滚优先**重部署先前验证过的不可变制品**；先检查数据库迁移、配置与仍受支持的客户端是否兼容。App 不能让已安装版本简单回退，通常通过新版本热修。
- 日常发布记录至少包含版本 / tag、源码 SHA、制品 ID、目标环境、关联任务、测试结果、发布人、审批人（生产）和发布时间；有 REQ 时关联 REQ 编号，纯 Bug 任务关联 Issue 或 PR。特殊发布另按 `3_特殊发布操作手册.md` §6 补充记录。

## 7. 例外处理入口

| 场景 | 处理文档 |
| --- | --- |
| Server main 不适合直接发布的紧急修复 | `3_特殊发布操作手册.md` §1 |
| App release 与 main 差异大，必须先修 release | `3_特殊发布操作手册.md` §2 |
| 提审前/发布当天无法完成回补 | `3_特殊发布操作手册.md` §3 |
| RC 被取消、release 基线偏离、需要核验 Git tree | `3_特殊发布操作手册.md` §4 |

**原则**：日常流程尽量轻，异常流程必须严；分支保护、CI、非作者 Review、可追溯制品与人工生产审批不能因团队小而取消。
