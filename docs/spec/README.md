# AI 辅助开发流程

- [需求模板](1_REQ-template.md)用于编写 L2/L3 的 REQ，填写后提交至独立需求仓库，通过 PR 评审并合入 main。
- [分支与发布规范](2_项目分支与发布规范.md)规定 Git、CI、合并和常规发布。
- [特殊发布操作手册](3_特殊发布操作手册.md)适用于紧急修复、回补及 RC 异常。

业务仓库各自维护 `AGENTS.md`，记录目录、构建与测试命令、环境和模块约束，并链接本流程及分支规范。

## 分级

| 等级 | 适用场景 |
| --- | --- |
| L1 快速任务 | 文案、局部 UI、普通 Bug、低风险重构 |
| L2 常规需求 | 独立页面、兼容的 API 扩展、常规业务逻辑 |
| L3 复杂或高风险 | 多仓库强耦合、设备协议、OTA、支付或权限、不可逆迁移、联合发布或重大兼容风险 |

产品和开发按风险共同分级。各等级在编码前、实施、PR 和验收各阶段的要求见下方矩阵。出现需求歧义、新的高风险或不可回滚风险时，暂停受影响部分并重新评估等级。需求按可独立验收、依赖明确、发布可控的原则拆分。

## 记录与资料

- **需求仓库**：独立 Git 仓库，保存 L2/L3 的 Markdown 需求文档；需求评审、业务确认和变更历史保留在 PR 与 Git 历史中。需求创建人检查仓库后人工分配唯一的 `REQ-123` 格式编号；需求 PR 合入 main 前再次检查编号，冲突时由尚未合入的 PR 调整。需求文档、代码 PR、最终提交和发布记录使用同一编号并通过链接关联（见分支与发布规范 §2）。正式 tag 标记实际上线版本，制品和上线结果以发布记录为准。
- **Git 仓库**：必要的技术决策、变更记录和验证证据，位于 Issue、PR 或已有技术文档。
- **发布记录**：发布制品标识、上线状态和发布结果；内容按分支与发布规范 §6 与特殊发布操作手册 §6 记录。
- L1 任务和纯 Bug 任务（不需要走 REQ 的修复）必须创建 Issue，可在 Issue 或关联 PR 中记录预期、方案和确认结论。两者无需创建 REQ 文档，各方记录通过链接关联。

推荐按需求交付版本创建目录。未排期需求由产品自行决定存放位置，不要求进入需求仓库；确定排期后，通过需求仓库 PR 完成需求评审并合入 `main`。交付版本用于组织需求，App、Server 和 Web 可使用各自的发布版本；跨版本需求保留一份主文档，避免复制多份。

设计资料使用固定版本链接或可回查的附件版本标识；未覆盖的界面状态应注明沿用的规则或交由产品确认。

## 各阶段要求

| 阶段 | L1 快速任务 | L2 常规 / L3 复杂·高风险 |
| --- | --- | --- |
| 编码前确认 | 创建 Issue，在 Issue 或关联草稿 PR 写明预期、方案要点和确认结论；开发负责人确认方案，业务行为变化先由产品确认预期 | 产品基于模板编写需求并提交需求仓库 PR；产品和开发评审范围、可验证 AC、依赖和主要风险，业务阻塞问题清零后合入需求仓库 main，再进入开发。**L3** 由技术负责人参与评审，确认关键契约、兼容及回滚风险 |
| 实施 | 提供 Issue 链接及关联草稿 PR 链接（如有），会话中的确认结论在编码前补入 | 以需求仓库 main 上已合并的 REQ 为依据，提供需求文档链接及设计、契约资料；AI 先读实际代码，待核实项记入执行记录 |
| 代码 PR | 链接 Issue 并标明编号，写明方案要点、AI 参与、变更范围，以及兼容、回滚和发布影响 | 链接已合并的需求文档并标明 REQ 编号，说明方案要点、实际改动和验证结果，以及 AI 参与、兼容、回滚和发布影响 |
| 验收 | 按影响范围验证；涉及业务体验时由产品在合入或发布前确认，并在上线后验收 | 产品需求预验收后提测、由测试验收；后端和 Web 在 dev 预验收、推广到 test 即提测；App 在功能冻结前完成预验收、自测和必要联调。**L3** 另覆盖 AC、边界及契约，完成专项验证 |

- **实施**：开发提供业务仓库路径；在任务分支或 worktree 进行，优先编写能表达 AC 的测试。已有测试覆盖可引用，无法自动化时说明原因并提供可执行的人工验证步骤。修改限于已确认范围。
- **技术记录**：L3 或涉及跨仓库契约、迁移和回滚的需求，在相关 Issue、PR 或已有技术文档中记录必要的关键决策及验证方式，不强制独立方案文档。
- **底线**：不得修改已执行的迁移脚本；不得为通过检查而删除有效测试或弱化有效断言。因已确认的业务变更调整测试时，在 PR 中说明原因，并保留或补充相应覆盖。
- **验证**：开发先自测，跨端和关键路径按需联调；补齐构建、lint、相关测试及适用的真机或联调验证；代码 PR 简述验证方式及结果，CI 中可查的内容直接引用，未执行的验证说明原因。
- **Bug 修复**：PR 记录根因、复现步骤。
- **阻塞项**：确认前清除业务阻塞项，提测前清除开发侧阻塞项，上线前清除测试和发布侧阻塞项；其他问题明确负责人和处理时点。
- **跨端协作**：跨仓库 PR 互链，跨端联调明确负责人。
- **合并与发布**：合入按分支规范的合并门槛执行；发布按分支规范执行，制品及上线状态记录在发布记录。
- **验收与测试结论**：L2/L3 由产品完成提测前需求预验收；涉及业务时由产品在上线后验收关键业务路径，无需记录产品验收结论。修复后复测受影响的 AC；测试侧阻塞项全部清零后，测试人员通过邮件或项目工作群向相关人员同步测试结论，并写明对应的 RC tag 和构建号；无 RC tag 或构建号时写明制品 ID，无需另写测试结果文档。CI 自动检查结果保留在 CI 中。

## 变更处理

- **A 类业务变化**（范围、用户行为、AC、设计口径）：暂停受影响部分；L2/L3 由产品通过需求仓库 PR 更新 REQ，按原等级重新评审并合入 main 后继续受影响部分，L1 和纯 Bug 任务在原 Issue 或 PR 中记录变化及必要的产品确认。开发同步更新方案和测试。
- **B 类关键技术变化**（接口、协议、数据契约、兼容、回滚或架构）：暂停受影响部分，由开发负责人确认新方案，L3 由技术负责人参与。通知受影响的调用方并补验证。
- **C 类边界内调整**（等价重构、辅助测试、文件组织）：可继续，在代码 PR 中简述重要差异。
- **记录**：A/B 类变更的必要技术决策及确认结论保留在相关 Issue、PR 或已有技术文档；L2/L3 的 A 类另在需求仓库 PR 和 Git 历史中保留 REQ 版本及产品确认；L1 和纯 Bug 任务记入原 Issue 或 PR。保留历史记录，按等级完成确认后再继续受影响部分。
